## 2. 第一轮结论

### 2.1 原来的“伴侣需要 / 生活方式”维度太宽

它混了：

- Need；
- Preference Shape；
- Relationship Process；
- Compatibility；
- Trade-off；
- Safety。

所以正式内容空间不能只写：

> “陪伴 / 空间 / 安全 / 责任 / 成长 / 边界”。

更准确是：

~~~text
Need Content
+ Need Shape
+ Fulfillment Mechanism
+ Fit Mode
+ Trade-off
+ Safety Boundary
~~~

单篇内容只取其中需要的部分。

### 2.2 Compatibility 不能简化成相似度

外部研究对人生目标、价值、人格相似性的结果显示：

- 一些相似性有小幅正向关联；
- 不同维度效果不同；
- 个人自身特点常常比简单相似度更能解释结果。

因此 Content 不做：

> “三观一样 = 一定适合。”

而是问：

> **差异是否进入重要生活、是否需要协调、双方能否协调。**

### 2.3 被理解 / 被回应需要从“情绪价值”里拆出来

当前网络语言里“情绪价值”很常见。

但 relationship science 的 responsiveness 更具体：

- understood；
- validated；
- cared for。

所以内容可以继续使用“情绪价值”作为用户入口词，但后台必须还原成具体关系过程。

### 2.4 自主和连接不是天然对立

SDT 明确把 autonomy、relatedness、competence 都视为关系中的基本需要，并强调 autonomy 不等于疏离。

所以：

> “独立的人就不需要亲密”

不能成为内容规则。

这非常适合做 Relationship 的反标签内容。

### 2.5 Need 和 Trait 不能一一对应

例如：

~~~text
Need：安全
≠
Trait：找一个“稳定的人”就完成

Need：被理解
≠
Trait：找一个“高情商的人”就完成
~~~

真正要通过 Scene + Process 看是否满足。

# 3. 当前来源偏差

## 3.1 Relationship 内部 Need 比外部平台资料完整

婚恋平台通常收：

- 对方条件；
- 自我标签；
- 择偶条件。

较少直接问：

- 你需要多少陪伴；
- 什么叫可靠；
- 你什么时候需要空间；
- 怎样的冲突方式让你最难受。

因此 Need/Fit Space 必须综合关系研究和真实体验，不能仅靠平台数据。

## 3.2 当前对性 / 亲密的用户语言仍偏少

学术证据足够说明性沟通和性自主支持是独立重要过程，但中国公开婚恋平台和一般调查里这部分表达较弱。

后续发布 / 评论验证时需要特别注意真实用户如何说这类需求。

## 3.3 Need Shape 的证据主要来自 Relationship 当前模型

门槛、舒服区间、条件性交换等结构目前主要是产品建模综合，而不是某一份单独调查直接给出的分类。

所以 N2 应继续作为 Local Model，并通过真实玩家 / 内容反馈验证。
